Writing

Notes from building things

Steganography is one of those ideas that sounds simple until you actually try to build it: hide information inside an image so it's invisible to the eye, but recoverable if you know how to look. During my cybersecurity internship with Edunet Foundation and IBM, I built exactly that — a Python tool that encodes hidden text into the pixel data of an image and extracts it back out.

The interesting part wasn't the concept, it was the details. Every image format handles pixel data differently, and a naive approach can visibly distort the image or get destroyed the moment the file is compressed or resaved. I had to think carefully about which bits I could safely modify without anyone noticing, and how to reliably locate that same data on the way back out.

It also reframed how I think about "hiding" versus "protecting" information — steganography hides that a message exists at all, while encryption protects a message people already know is there. Understanding that distinction changed how I now think about data protection problems in general, not just this one project.

I built Neox expecting the challenge to be about clever responses. It wasn't. The real challenge was intent — figuring out what a user is actually asking, when people phrase the same question a dozen different ways.

Early versions of Neox were painfully literal: a slight rewording of a question the bot "knew" would make it fail completely. Getting past that meant thinking less like a programmer chasing exact string matches, and more like someone trying to understand a conversation — normalizing input, matching intent instead of exact phrasing, and always having a graceful fallback instead of a dead end.

That lesson ended up mattering beyond the project itself — it shaped how I think about any user-facing interface, portfolio included: meet the user where they are, don't make them guess your syntax.

Across my internships with TechnoHacks and Edunet/IBM, I spent a lot of time on the other side of software — analyzing traffic with Wireshark, tracing simulated attacks, and thinking through how systems fail rather than how they're supposed to work.

That perspective followed me back into development. When I write a Spring Boot service now, I find myself asking different questions than I used to: what happens if this input isn't what I expect? What does this endpoint expose if someone probes it directly? It's a small shift, but it's made me a more careful engineer — not paranoid, just deliberate.

I don't think you need a cybersecurity background to write good code, but having one has made the habit of thinking about edge cases and failure modes second nature, and that's stuck with me across every project since.
